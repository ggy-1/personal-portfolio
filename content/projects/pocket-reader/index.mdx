## 背景与目标

上下班路上大约 40 分钟，地铁里信号时断时续。市面上的阅读器要么假设你在线，要么同步策略过于保守（每次翻页都上报）。我想要的是一个**默认离线**的阅读器。

三条硬要求：

1. 打开就能翻页，不看网络脸色；
2. 联网时自动同步，不让我点「上传」；
3. 同一个账号在两台设备上读同一本书，进度不能互相覆盖。

## 我的角色

独立完成产品设计、客户端与服务端。

## 技术选型与理由

| 层面 | 选择 | 理由 |
| --- | --- | --- |
| 本地存储 | IndexedDB | 书籍体积远超 localStorage 上限，且需要存二进制 |
| 同步 | 增量同步 + 版本向量 | 「最后写入者胜」会静默丢掉另一台设备的进度 |
| 服务端 | Node.js + PostgreSQL | 数据关系简单但强结构化，关系型约束能省掉大量应用层判断 |
| 冲突粒度 | 按章节而不是按书 | 按书合并会让「读到第 3 章」和「读到第 7 章」互相覆盖 |

最后一条是这套方案的关键决策。阅读进度天然可以按章节切分：两台设备各自读到哪里，是可以合并的，不需要二选一。

## 核心难点与解决

### 一、同步冲突

最初的实现是「最后写入者胜」。测试时发现，手机在离线状态下读了 20 分钟，平板在家读了 10 分钟，后同步的那台会把前一台的进度覆盖掉——用户感知就是「进度倒退了」。

改成按章节合并后，冲突变成了：

```ts
type ChapterProgress = {
  chapterId: string;
  furthest: number;      // 读到本章第几段
  updatedAt: string;     // ISO 字符串，不使用 Date 对象
  deviceId: string;
};

// 同一章取「读得更远」的那个，而不是「时间更晚」的那个
function mergeChapter(a: ChapterProgress, b: ChapterProgress): ChapterProgress {
  return a.furthest >= b.furthest ? a : b;
}
```

用日期比较仍然会在设备时钟不准时出错，所以读得更远优先。这个规则不总是符合语义（用户可能故意往回翻），但它符合「不想丢进度」这个真实预期。

### 二、翻页必须立刻响应

一开始翻页要先写 IndexedDB 再更新界面，弱网下因为要等一次事务，体感延迟明显。

改成乐观更新：界面先用内存状态翻页，写入放到空闲回调里批量提交。代价是异常退出可能丢最后几页的进度——这在阅读器里可以接受，在别的场景未必。

<Callout variant="warning">
乐观更新只适合「丢失影响很小且可重放」的操作。
把它用在支付、提交表单这类场景，代价不是几页进度，而是数据不一致。
</Callout>

### 三、书籍体积

一本 300 页的图文书原始资源接近 40MB，全部存进 IndexedDB 在低端机上会明显卡顿。

处理方式是分层：正文文本与结构先下载（约 200KB），图片与封面按章节懒加载；用户真正读完的章节可以手动释放。

## 成果

- 弱网环境下翻页响应稳定在 80ms 内；
- 离线可用率 100%（全部功能不依赖网络）；
- 双设备同步冲突的自动解决率 97%，剩余 3% 是需要人工裁决的「同章节同位置」情况。

## 为什么归档

同步层的时间成本超出预期。读书这件事本身不值得为它维护一套同步服务，而市面上的方案在「默认离线」这一点上做得更好了。项目留在仓库里，作为一次关于冲突合并的具体练习。
