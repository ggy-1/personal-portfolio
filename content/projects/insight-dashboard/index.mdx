## 背景与目标

这是一套内部数据看板，累计 4 年迭代、约 180 个页面，技术栈是 jQuery + 服务端模板拼接。它的问题不是「技术老」，而是：

- 同一个筛选逻辑在 40 多个页面里各写了一遍，改一处要改 40 处；
- 所有页面共用一个 1.2MB 的 JS 文件，首页要等它全部下载解析完才能跑；
- 没有类型约束，接口字段改名只能靠运行时发现。

目标很明确：**在不中断业务的前提下迁移到 React + TypeScript**。这套系统每天有数百人使用，下线维护窗口是不现实的。

## 我的角色

前端负责人，负责技术方案、迁移顺序、公共库设计与代码评审。

## 技术选型与理由

| 层面 | 选择 | 理由 |
| --- | --- | --- |
| 迁移方式 | 按模块灰度替换 | 整体重写的风险不可控，且没有可以停机的窗口 |
| 通信机制 | 事件总线 + 独立的挂载根 | 新旧代码需要并存，事件总线让二者不需要知道彼此存在 |
| 构建 | Vite + 多入口 | 每个灰度模块一个入口，产物互不影响，回滚只需摘掉入口 |
| 状态 | 先用 React 内置能力 | 4 个页面证明内置能力够用之后，才引入额外的状态库 |

最后一条是刻意的克制。迁移期间最容易失控的是「顺手把架构也换了」，所以我们把每周新增的依赖数量写进了周会指标。

## 核心难点与解决

### 一、新旧代码共存

jQuery 直接操作 DOM，React 也管理 DOM，两者作用在同一棵树上必然互相踩。解决办法是**约定挂载边界**：每个新页面独占一个根节点，jQuery 只允许操作边界之外的内容。

为了让边界可验证，我们写了一个开发期断言：React 的根节点如果被外部修改，控制台直接报错。这比事后排查 DOM 冲突便宜得多。

### 二、首屏 3.2s

拆开之后发现，3.2s 里有 1.8s 花在一个只在设置页用的图表库上——它被打进了全局 bundle。

按路由拆分 + 把图表库改成动态 import 之后，首屏降到 1.1s。这里的关键不是「动态 import」这个动作，而是**先量出来谁在首屏下载里**。

### 三、类型从零建立

没有类型定义的后端接口，直接手写 interface 会写出一堆猜测。做法是：

1. 先用 `unknown` 接住响应；
2. 用 Zod 在边界处校验一次，把校验结果作为类型的唯一来源；
3. 类型从 `z.infer` 派生，而不是手写。

这样接口字段改名时，问题会在校验层暴露，而不是在某个深层组件里以 `undefined` 的形式出现。

## 成果

- 首屏从 3.2s 降到 1.1s，首屏 JS 减少 62%；
- 40 份重复的筛选逻辑收敛为一个公共模块；
- 灰度期间零业务中断，每个模块都可以单独回滚。

## 如果重做一次

我会更早地写「边界断言」这类开发期检查。共存期的 bug 有一半来自越界操作，而它们在小范围测试时几乎不会出现，只在真实页面上偶发。
