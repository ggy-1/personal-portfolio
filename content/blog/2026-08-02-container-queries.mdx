同一个卡片组件，放在侧栏里显示两行文字，放在主区域里要显示封面图加摘要。用媒体查询写这件事，你需要给卡片加一个 `variant` prop，再在页面里判断它被放在哪一栏。

问题在于：**组件不应该知道外部容器的宽度决策。**

## 媒体查询的错位

媒体查询的断点描述的是视口，而组件要适配的是它自己被分配到的空间。这两者在大屏上分叉得最厉害：一个 1440px 的视口里，侧栏可能只有 280px，主区域有 800px。在这两个位置渲染同一个卡片，媒体查询给出的答案完全一样——都是「桌面」——所以它帮不上忙。

于是就有了 `variant`、`layout`、`size` 这类 prop 的泛滥。每个 prop 都是一次「让父组件替子组件做决定」，调用方要读组件实现才知道该传哪个值。

## 容器查询的做法

声明一个容器，然后用 `@container` 写断点：

```css
/* 父级声明自己是查询容器 */
.card-slot {
  container-type: inline-size;
  container-name: card;
}

/* 卡片自己决定在什么宽度下长什么样 */
@container card (min-width: 420px) {
  .card {
    grid-template-columns: 160px 1fr;
  }
}
```

`container-type: inline-size` 让浏览器为该元素建立包含块，`inline-size` 表示只跟踪行内方向（宽度）——这也避免了容器尺寸依赖内容尺寸造成的循环。

Tailwind CSS 4 对这些语法有一层映射，写起来更短：

```html
<div class="@container">
  <article class="flex flex-col @md:grid @md:grid-cols-[160px_1fr]">
    <!-- 这里的 @md 判断的是最近的容器，不是视口 -->
  </article>
</div>
```

注意 `@md:` 和 `md:` 的区别只在前缀符号上，但语义完全不同：前者读容器，后者读视口。混用时最容易写错的就是这里。

## 边界情况

容器查询不是媒体查询的替代品，两者的分工很清楚：

| 场景 | 用什么 |
| --- | --- |
| 整站栅格列数、导航形态 | 媒体查询（取决于视口） |
| 组件内部布局随可用宽度变化 | 容器查询 |
| 打印样式、`prefers-reduced-motion` | 媒体查询 |
| 侧栏宽度由用户拖拽决定 | 容器查询 |

容器查询解决不了「视口很窄但容器被显式设为 600px」这种矛盾情况，那时会被压扁的仍然是内部元素。这类情况需要在外层限制 `max-width`。

<Callout variant="info">
`container-type: inline-size` 会让容器成为一个包含块，内部的绝对定位元素会以它为参照，
`position: fixed` 的后代也会受影响。给已有组件套容器查询之前，先确认里面没有依赖视口定位的元素。
</Callout>

## 实际收益

在项目里落地后，两件事同时消失了：

1. 卡片组件的 `variant` prop 被删掉，调用方不用再传布局参数；
2. 因为布局不再由页面决定，卡片被挪到别的容器里不需要改任何代码。

代价是浏览器支持门槛：容器查询需要 Chrome 105+ / Safari 16+ / Firefox 110+，这已经落在 PRD 里「最近两个版本」的范围内，不需要 polyfill。

## 小结

判断用哪个查询，只需要问一句：**这个决定取决于视口，还是取决于我被放在哪里？** 前者用媒体查询，后者用容器查询。
