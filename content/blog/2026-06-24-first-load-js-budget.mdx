性能优化里最贵的一句话是「先加上，以后再优化」。它把一次可以避免的成本变成了一笔技术债，而且这笔债会随着依赖数量复利增长。

真正让体积不再失控的，不是某个优化技巧，而是**一个写进 CI 的数字**。

## 预算怎么定

定预算的常见错误是从「别人的站点」抄一个数字。正确的顺序是从自己的约束倒推：

1. 目标网络条件：4G，实测下行约 1.6Mbps，RTT 约 150ms；
2. 目标 LCP：2.0s，其中留给 JS 解析与执行的时间不超过 800ms；
3. 中端安卓机的 JS 执行速度按 1MB/s 估算——那么首屏 JS 就落在 150KB 左右。

这个数字不是精确计算出来的，而是**量级正确的**。它的作用不是预测真实耗时，而是给「能不能再加一个依赖」提供判断依据。

| 项 | 预算（gzip） |
| --- | --- |
| 首屏 JS 合计 | 150KB |
| 框架运行时 | 100KB |
| 单页 CSS | 40KB |
| 单个新增依赖 | 10KB |

## 把它写进 CI

预算只有变成断言才有约束力。最直接的做法是在构建后读取产物清单，逐条比对：

```ts
const budgets = { firstLoadJs: 150 * 1024, pageCss: 40 * 1024 };

for (const [route, size] of Object.entries(manifest.routes)) {
  if (size.firstLoadJs > budgets.firstLoadJs) {
    throw new Error(`✗ ${route} 首屏 JS ${size.firstLoadJs}B 超预算 ${budgets.firstLoadJs}B`);
  }
}
```

报错信息必须包含**路由、实际值、预算值**三样，否则开发者看到「超出预算」之后还得自己去翻产物目录找差距。

<Callout variant="warning">
不要在超预算时只打印警告。CI 里所有人都只看最后一行绿色的 PASS，
警告等于没写。要么失败，要么删掉这条规则。
</Callout>

## 踩过的坑

### 第一版断言被绕过

一开始我只检查了总产物的体积。结果是单页超了、总体没超，CI 一路绿灯。要按**路由**而不是按总量断言——总量会掩盖单页的异常增长。

### 动态 import 也会进预算

把一个大依赖改成 `await import()` 只解决了首屏问题，没有解决体积问题。它变成了一个独立的 chunk，只有真正被使用时才下载。但如果那个「真正被使用」的时机是首屏渲染后 200ms，用户实际上还是付了这份钱，只是付费时间点被推后了。

判断标准是**用户是否必须立刻用到**，而不是「它是不是在首屏渲染之后加载」。

### 依赖的类型包也算数

`@types/*` 不参与运行时体积，但它会把传递依赖带进 lockfile，进而影响最终产物。真正需要看的是 `pnpm why <pkg>` 给出的引用链，而不是 `package.json` 里那一行。

## 意料之外的收益

预算表跑了一个季度之后，最大的收益不是体积数字，而是**它改变了讨论方式**。

以前评审新依赖的对话是「这个库挺好用的，加上吧」；现在是「它 12KB，超过 10KB 的门槛了，能说说不加它我们缺什么吗」。

前者没有裁判，后者有。多数时候，答案会在第二次提问时变成「其实手写 20 行也能用」。

## 小结

1. 从网络条件和目标指标倒推预算，不要抄别人的数字；
2. 按路由断言，把实际值、预算值、路由名都写进报错；
3. 把预算表当作评审新依赖的裁判，而不是性能优化的终点。
